# Task 3 — browser task API, personal keys, and final-status recurrence

Status: implementation verified locally on `feat/tasks-api-mcp`. No configured Supabase project, production database, real integration key, or `.env` was accessed or changed. All HTTP tests use mocked browser sessions/responses; the SQL runner uses only `omnia-tasks-api-test` and its dummy baseline.

## Behavior and owned files

- `apps/web-next/src/repositories/tarefasRepo.supabase.ts`: keeps the compatibility export but routes task list/get/search/create/update to `/api/v1/tasks`; paginates through opaque cursors and retains stable descending `(createdAt,id)` order. DTO conversion covers refs, nullable historical fields, counts, tags, privacy, opportunity and recurrence. Local `YYYY-MM-DD` uses local-midnight components in both directions. `wireUpdatedAt` retains the exact API timestamp, including microseconds, and `taskEtag` builds the strong `If-Match`; `Date.toISOString()` is never used for the version. Explicit nullable clears survive as `null`; unchanged fields are omitted. A transport retry reuses the same idempotency key and payload. A stale 412 gives a Portuguese reload message and is never replayed as an unconditional update. No in-memory cross-user task cache was introduced. Existing delete remains on its prior Supabase path because v1 has no delete route. `listTaskAssignees` uses the official endpoint.
- `apps/web-next/src/stores/tarefas.store.ts`: inline edits use the task currently shown in the store as the original for CAS. Edit forms pass their loaded original explicitly. Store/API errors retain the meaningful API message.
- `apps/web-next/src/components/tickets/TicketForm.tsx`, `apps/web-next/src/components/tickets/TicketAssigneeSelect.tsx`, `apps/web-next/src/app/tarefas/new/page.tsx`, `apps/web-next/src/app/tarefas/[id]/edit/page.tsx`: full human recurrence inputs remain available, with local calendar date conversion. Browser-generated counts/cursor and recurrence RPC are removed. The form sends complete values, including status; the adapter omits unchanged fields so a completed occurrence's unchanged status does not contaminate a configuration-only patch. When another human form field changes on a series, recurrence configuration accompanies that field so the future template also changes. Private assignment uses the domain `userProfile.id`, not `auth.users.id`; the candidate list comes from `/api/v1/task-assignees`. A debounced server search reaches eligible users beyond the first 100, while the current selected assignee remains visible even outside that first page. Attachment creation stays on its existing separate path.
- `apps/web-next/src/hooks/useTarefasOportunidade.ts`: linked tasks use the official task API with `oportunidadeId` and dynamic UUID status metadata from `/api/v1/task-statuses`, replacing raw Supabase REST and hard-coded status labels. Dashboard/store task reads and the existing task-page realtime refresh remain wired through the adapter. `apps/web-next/src/components/notifications/NotificationsBootstrap.tsx` and `NotificationsMenu.tsx` now resolve task titles through official task detail reads, preserving private-task authorization; the bootstrap context cache resets when the authenticated user changes. Ata/comment notification reads remain on their separate paths.
- `apps/web-next/src/repositories/integrationKeysRepo.api.ts`, `apps/web-next/src/app/integracoes/page.tsx`, `apps/web-next/src/components/layout/AppSidebar.tsx`: any authenticated user can reach personal integration keys in the sidebar footer without task/admin menu permission. The page lists audience, scopes, expiry, revocation and last use; creates API or MCP keys with chosen read/create/update scopes and server-default 90-day expiry; copies the flat one-time `data.token`; clears it on dismissal/unmount/revocation and blocks another creation while it is visible. Replacement creates a new key before revoking the old one; a revoke failure remains visible after refresh. The secret is only React state, never URL/storage/log output. The page refers users to administrator-provided client configuration without presenting an undeployed endpoint as live.
- `supabase/migrations/20261002223637_tasks_api_transactional_security.sql`, `supabase/tests/tasks-api/review-regression.sql`: root-authorized narrow canonical fix. An explicit final `statusId` on a human full-form recurrence PATCH completes that occurrence but does not copy final status into the future series template. Other explicit fields still update the template and generation creates a pending next occurrence.
- Tests: `apps/web-next/src/repositories/__tests__/tarefasRepo.api.test.ts`, `apps/web-next/src/stores/__tests__/tarefas.store.api.test.ts`, `apps/web-next/src/hooks/__tests__/useTarefasOportunidade.test.tsx`, `apps/web-next/src/app/integracoes/__tests__/page.test.tsx`, `apps/web-next/src/components/layout/__tests__/AppSidebar.test.tsx`, `apps/web-next/src/components/tickets/__tests__/TicketAssigneeSelect.test.tsx`.

The baseline ticket `updated_at` trigger calls `clock_timestamp()` (`supabase/tests/tasks-api/baseline.sql:128`), so same-transaction fixture updates visibly advance. The repository's production trigger calls `public.update_updated_at_column`; its later migration definition assigns `now()` (`supabase/migrations/20250909020000_create_omnia_administradoras.sql`). The browser uses the exact wire timestamp either way. The isolated fixture is not proof of the production trigger's clock behavior.
