# Omnia tasks API and MCP implementation plan

Approved conversational design, 2026-10-02. Branch: `feat/tasks-api-mcp`.

## Goal and constraints

Grok Bot -> independent MCP HTTPS server -> official Next.js API -> shared task services -> persistence. MCP must have no database connection, Supabase dependency, business rules, SQL tool, or arbitrary HTTP forwarding. Keep existing UI behavior and move equivalent task operations to the shared service/API. Keys belong to the existing Omnia user, not a bot account. Their effective access is the intersection of live user permissions and `tasks:read`, `tasks:create`, `tasks:update`. My tasks is an optional assigned-user filter. Private tasks are visible to their creator and ADMIN. Direct authorized writes need no approval queue. Pilot creates standalone tasks and updates existing recurrence occurrences; recurrence configuration is not available to integration keys. Keep existing human recurrence configuration working. No MCP deletion/comments/attachments. Do not mutate production database, deploy, merge, or expose real secrets during implementation; inspect production schema only. Preserve existing untracked `.context/` artifacts.

## Task 1: transactional persistence and security

Create migration(s) using `supabase migration new`. Add private credential/session/audit/idempotency/rate-limit records. Persist token digests, actor binding, resource audience, scopes, expiry/revocation. Service-only public RPC invokes private implementation owned by a non-table-owning NOLOGIN NOBYPASSRLS role, with finite operation allowlist and transaction-local verified auth identity for existing RLS/notification triggers. Reconcile task RLS to creator/ADMIN privacy and protect profile privilege columns. Do not use privileged table writes as authorization. Preserve sequence-generated ticket ID, counters and assignment trigger identity. Local tests must use restrictive production-equivalent policies, not broad UI fixture policies.

Operations: list/get/create/update tasks, read statuses/eligible assignees, list/create/revoke own credentials, exchange MCP credential for short-lived API-only session. DB inputs contain verified browser auth identity OR a credential/session digest, never a client-selected actor. All task operations recheck expiry/revocation/active actor/menu permission. Backend-only MCP exchange authenticates its service credential in the API. Creation and update are atomic with idempotency and audit. Cursor pagination default 50/max 100, stable created_at/id. Update checks expected updated_at and supports explicit null clearing. Limit recurrence completion to the authorized series and next occurrence, deduplicated across retries/reopening; preserve cron generation, reusing common generation helper. Human series writes remain transactional; reject derived series counters from external input.

## Task 2: official Next.js API and shared service

Create Zod HTTP DTOs independent of browser Tarefa, task service/repository using RPC from Task 1, verified Supabase browser-session guard and integration-key guard. Endpoints: GET/POST `/api/v1/tasks`, GET/PATCH `/api/v1/tasks/{id}`, GET `/api/v1/task-statuses`, GET `/api/v1/task-assignees`, own-key management and backend-authenticated MCP credential exchange. JSON envelopes include data/error + requestId, read task ETag, PATCH If-Match, write Idempotency-Key. Due dates YYYY-MM-DD, timestamps ISO; generated ticketId distinct from ticketOcta. Resolve user references from IDs, reject audit/counter IDs and invalid references. Separate API/MCP audiences: incoming MCP key cannot invoke resources directly, direct API key cannot connect to MCP. Exchange produces short-lived API-only capability retaining parent key, and every resource request rechecks parent revocation. Keys default 90-day validity, raw values returned only once.

## Task 3: shared UI task flows and key management

Switch equivalent task list/detail/create/update and inline operations to official API with typed browser adapter, preserving realtime refresh, dashboard and linked task readers. Keep comments/attachments separate. Preserve human recurrence configuration with internal human capabilities; fix auth ID/domain ID confusion and date/null clearing. Add personal integration-key UI (ordinary authenticated users), list metadata, create API/MCP keys, copy one-time secret, revoke/replace, clear explanations of identity/scope. Do not put secrets in URL/logs/chat examples.

## Task 4: independent MCP workspace

`apps/mcp-server`, Node/TypeScript official MCP SDK, stateless Streamable HTTP, compatible with older clients. Fixed tools list_tasks/get_task/create_task/update_task/list_task_statuses/search_task_assignees. Validate inputs, consume fixed API routes only. Exchange per-user MCP secret through official API; do not store per-user API keys. Preserve If-Match/idempotency during calls, structured tool errors, timeouts, HTTPS URL validation, safe logs. Independent Vercel deployment; root scripts/workspaces/lockfile and CI include its tests/build/type checks. Client+server integration tests exercise real MCP transport against controlled HTTP API.

## Task 5: verification and documentation

Document API via OpenAPI, key lifecycle, Grok Bot custom HTTPS connector setup, variables, deployment order, read/write kill switches and revocation. Verify restrictive local DB: real role RLS, user overrides, private isolation incl ADMIN, author/notification identity, revoked/expired keys, disabled user, forged fields, parent revocation after exchange, idempotent retries, stale update, recurrence target isolation, no effect on unrelated series, rate limits, transaction rollback, no context leakage. Run web Vitest, MCP tests, lint/type checks, build and appropriate UI smoke tests. Actual Grok account setup is a deployment gate and requires target account/config after branch is reviewed. Root controller reviews each task plus whole-branch diff; commit verified changes with Conventional Commits; never stage unrelated artifacts.
